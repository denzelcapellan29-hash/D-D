# Blender → 3D Canvas Runtime Contract — DM Decision 2026-10-22

**Decision status:** USER-DIRECTED ARCHITECTURAL INTENT, not a claim of an implemented full-world importer, final runtime selection, or accepted art. At this point Blender authoring is authoritative; evaluate 3D Canvas as playable 3D runtime. This explicit instruction supersedes historical Foundry-first building proposals and does not require discarding Godot experiments before fair comparison.

## 1. Responsibilities / ownership
- **Blender authoritative:** Official source-map topology, geometry, source asset provenance, architectural placement, coordinate space, authored landscape, material reference, approved artist-facing composition, object identities and animation/reference camera shots. Follow live AI 3D Asset Workflow and environment-specific lanes, with numbered checkpoint files, original GLBs/approved derivatives, QA and DM acceptance.
- **Export bundle:** Stable machine-readable scene manifest plus purpose-specific GLBs and PBR textures, optional bundled animations; object-hierarchy canonical transforms, anchor/pivot, bounding boxes, asset hash and provenance, expected scene extents, collision/visibility classification, door groups and explicit gameplay markers. Do not treat a JPG/2D composition render as a 3D scene.
- **MCP importer:** Version-specific 3D Canvas document/flags translator using actual Foundry V14 scene grid metrics. Deterministic, idempotent update/delete-by-owned-semantic-ID on a duplicate/new test Scene, source-asset file validation, preflight, no vendor source modifications, actual post-creation measurement, rollback, numerical+image QA.
- **3D Canvas runtime:** Native GLB/3D Tile rendering, collision and camera collision, per-token movement and selected player's first-person POV, 3D line-of-sight/visibility settings, doors, lighting, Cutscene engine and interaction. Foundry remains mechanics, sheets, initiative, journals. Run browser/client gameplay QA and verify no secrets exposed.
- **Runtime-specific overlay:** Store Foundry-only token, journal, cutscene, sound, lighting behavior and permission settings separately and preserve them across Blender re-exports. Changes to runtime overlays must not silently mutate authoring geometry; visual geometry changes return to Blender.

## 2. Faithful geometry without hand-building in Foundry
1. Export **large static coherent chunks** (room shell, terrain section, ceiling/roof sections, architectural zone) as GLBs with proper world/object transforms and measured bounding boxes. Avoid exporting entire scene as one unmanageable mesh: interactive doors, visibility layers, selective occlusion, performance and local rollback require separability.
2. Export **interactive/movable parts** (doors, doorsets, hazard components, selected props) as independently identified GLBs or as documented GLTF submesh hierarchy with native custom properties. Never manually re-place hundreds of tiny Meshy meshes as independent authoring.
3. Export a deterministic manifest with source object UUID/name, asset source and SHA256, `matrix_world` decomposition with quaternion and orientation, parent/root transform, Blender meter scale, Foundry scene pixel/grid scale, pivot, AABB/OBB, intended ground contact, target tile/document type, sight/collision/camera-collision/door flags, static vs dynamic and artifact version. Explicit mapping between Blender up-axis/world and 3D Canvas X/Y/Z, validated on landmarks. No hard-coded 100px=5ft global assumption.
4. Convert coordinates once using a tested, invertible affine/world transform and apply to each object; check relative distances, scaled mesh dimensions, yaw/orientation and vertical elevation across both engines. Report actual residuals and root/parent double-transform hazards; visually inspect aligned overhead and player-eye captures.
5. Preserve PBR appearance with traceable bakes/texture paths. Different real-time renderers will not be perfectly pixel-identical to Blender cycles; target **mesh and layout identity plus art-directed visual parity** and document any purposeful engine lighting adjustments. Genuine physical geometry must remain present.
6. Runtime-specific colliders/vision/door flags can be authored in Blender GLTF custom properties and/or generated by a **manifest overlay** when supported by the installed version. Official Tiles documentation: `collision`, `sight`, `isDoor`, `doorId`, `ds`, `doorStyle`, `doorAnimateAngle`. Configure Block Movement, Block Sight and Camera Collider independently per relevant Tile; grass/transparent decor should not unnecessarily block everything. Documented import behavior must be verified on actual native runtime and not inferred merely from successful JSON persistence.
7. Do not promote collision meshes/proxies outside accepted workflow. Runtime collider metadata is permitted; any physical visible-geometry changes must respect selected skill/source authority.

## 3. Exactness, invariants and QA gates
- **Geometry import:** same visible asset parts and scene structure, no missing/extra mesh, no negative/mirrored unexpected scaling, same landmark/portal/entrance alignment and ground-contact grade. Use numerical per-object transform residuals, seam sampling and bounding volumes; compare actual Blender/Foundry screenshots of equivalent camera positions, including behind walls, elevated and far-field view. Establish tolerances on a small fixture before bulk import rather than declaring false absolute pixel identity.
- **Walkability:** per-player first-person movement and independent camera control, occupied doorway/corridor clearance, floors/elevations/slopes, stair climbs/descents, unwalkable pit/roof rejection, jump/fall prevention, camera collision from player eye, restoration after cutscene, absence of clipping through walls and ceilings.
- **Visibility:** distinguish visual renderer camera FOV from token sight/field-of-view cones and fog exploration. Native 3D geometry sight supports token occlusion but fog exploration is 2D in documented 3D Canvas; require actual test for directional sight cones and character-specific darkvision. Source `https://wiki.theripper93.com/levels-3d-preview/info/fow`.
- **Interactive:** doors locked/opened/closed and sight/collision synchronized, trigger/cutscene permissions, GM cutscene play/pause/skip/restore and player return, no GM-only secrets visible.
- **Performance:** compare calibrated Blender render reference against real Foundry player client with scene active and identical composition. Record FPS/frame time/GPU memory/asset draw calls at initial load, walking, first-person, cutscene and overhead views. Previous Area8 screenshot had approx 25 FPS and performance Grade E; this is a warning requiring actual test on appropriate viewport, not a general platform rejection. Optimize derivatives/chunking only after measured bottlenecks, preserve originals.
- **Persistence/regression:** restart Foundry client and re-open the same Scene, recapture player-eye, verify per-object manifest hashes, first-person settings and restored camera, reload no new garbage Tiles or duplicates. Retain verified restore point/scene clone, not modify accepted Area8 on first spike.

## 4. First vertical-slice fixture (before full room)
A small source-indexed and opt-in **disposable** Blender scene segment: four connected approved floor modules (or a coherent terrain patch for outdoor lane), two adjoining architectural wall modules, a compatible ceiling/roof, one door, one light, one physical obstacle, walkable spawn/exit path, at least one approved prop, with a source-authored overview camera and player-eye camera. First Blender QA PASS, then export chunks/manifest, implement version-safe importer into a cloned/new Foundry Scene, verify exact geometry/visual alignment. Two player QA tokens (monk, druid equivalents) need independent POV, collision and sight/darkvision checks. One cutscene camera path enters and restores player control. Explicit gates:
- A: GLB import parity; geometry and scale PASS.
- B: walkability and physical/camera collision PASS.
- C: token sight/LOS, player-vision cone expectation, darkness and fog limits PASS or disclose unsupported.
- D: cutscene play/restore PASS.
- E: material/render/performance and far-field world continuity PASS and DM visual acceptance separately.
If gate FAIL, revise exporter/importer architecture before replicating full scenes. Do not fake success with static hero render or JSON save alone.
