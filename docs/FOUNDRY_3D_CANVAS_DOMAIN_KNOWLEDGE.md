# 1. Core mental model

## Foundry is document state; 3D Canvas is a live renderer layered over it

A Foundry Scene can contain valid Scene, Tile, Token, AmbientLight, Region, Note, Wall, and other documents while the 3D Canvas runtime is still missing, stale, unloaded, misconfigured, or visually wrong.

Therefore:

- serialized Scene JSON is **not** render truth;
- document counts are **not** render truth;
- a successful API response is **not** render truth;
- the live Three.js/3D Canvas runtime plus a visible capture is render truth.

Every production 3D change must end with live runtime inspection and player-facing visual QA.

## Scenes are the runtime containers

Scenes own the placeables and environmental configuration. Use separate Scenes when there is a meaningful presentation/runtime boundary, but do not fragment the campaign merely because an encounter exists. The campaign's semantic world model remains canonical above Foundry.

## Use core Foundry concepts before modules

Baileywiki's Foundry Basics series repeatedly reinforces learning the core object model and normal workflows first: Scenes, Actors/Tokens, Walls/Doors, Lights/Vision, Journals, Tables, Playlists/Sounds, Compendiums, files and permissions. Modules should extend those workflows, not replace understanding of them.

# 2. 3D Canvas construction model

## Tiles are the primary 3D building primitive

Current 3D Canvas documentation calls Tiles the “bread and butter” of 3D map building.

Use 3D Tiles for:

- floors;
- walls/structural pieces;
- ceilings/roofs;
- doors;
- props;
- terrain;
- decorative geometry;
- collision and sight geometry when appropriate.

Do not default to large numbers of ordinary Foundry Walls to construct a 3D environment. 3D Tiles can block movement/sight and can function as doors.

## Prefer the native 3D placement lifecycle

The normal supported workflow is:

1. enter 3D mode;
2. use the Tiles layer / 3D-aware file picker or Asset Browser;
3. place the GLB/GLTF model;
4. let 3D Canvas create/initialize the Tile;
5. manipulate it with the 3D gizmo;
6. tune the 3D tab settings.

Automation should reproduce the state produced by this lifecycle, not assume that arbitrary syntactically-valid Tile JSON is equivalent.

This is a critical lesson from the failed Episode 1 full-dungeon build.

## Model tiles and Dynamic Meshes are different construction modes

Do not casually mix a model-backed Tile with Dynamic Mesh state.

- Model-backed Tile: uses a GLB/GLTF/FBX reference.
- Dynamic Mesh Tile: procedural/basic geometry generated by 3D Canvas.

Treat them as separate semantic types in the generator.

For model-backed Tiles, preserve the model reference and normal positioning/material fields.
For Dynamic Meshes, explicitly define the mesh primitive and its dimensions/material/heightmap/noise settings.

## Prefer GLB/GLTF

GLB/GLTF is the preferred model format. FBX is legacy/phasing out.

Custom source-specific assets should normally be exported as GLB.

## Positioning defaults matter

3D Canvas exposes Auto Ground, Auto Center, tilt and depth controls because source models do not all share the same pivot/origin conventions.

For automated placement:

- know whether the asset expects auto-grounding;
- know whether it expects auto-centering;
- verify its live runtime bounds;
- never infer the rendered 3D center solely from Foundry's 2D `x/y/width/height` fields.

A Tile's 2D Foundry bounds and its 3D runtime bounds are related but not interchangeable coordinate descriptions.

## Placeholder 2D image is part of normal Tile creation

The supported 3D Tile placement workflow assigns a placeholder 2D image so the Tile remains identifiable/usable from Foundry's 2D layers and legacy visibility logic. Do not assume an empty texture source is harmless.

## Collision/sight should be intentional

For 3D Tiles:

- Block Movement only when geometry should physically obstruct tokens.
- Block Sight only when needed; unnecessary sight geometry costs performance.
- Floors, grass, decorative clutter, many trees/props generally do not need sight blocking.
- Camera Collider is separate and only matters to camera behavior.
- Doors can be represented by Tile door properties.

Player-facing context geometry should often have collision/sight disabled until the spatial art pass is validated.

## Repeated props should be optimized

3D Canvas provides Repeat/tiling and Merge/Auto Merge because hundreds of individual repeated objects are expensive.

Workflow:

1. build/art-direct while modular;
2. validate collision, sight, doors and visuals;
3. snapshot/duplicate;
4. merge compatible static repeated Tiles;
5. never merge interactive door elements that need independent state.

# 3. Mapmaking Pack / Advanced Tools

The Mapmaking Pack is not merely an asset folder. It provides mapmaking workflows:

- Asset Browser;
- Material Browser;
- Environment Panel;
- Terrain tools;
- token browser;
- Dungeons & Interiors tooling;
- Effects;
- Cutscenes;
- Community Maps.

Use these systems as the visual vocabulary before generating custom geometry.

## Asset-first rule

Resolution order:

semantic role -> installed 3D asset/material/prefab -> procedural/dynamic mesh adaptation -> custom GLB only if source-specific geometry cannot be represented adequately.

Do not build a custom monolithic GLB simply because procedural generation is possible.

## Materials are first-class

Geometry and materials are separate concerns.

A scene's quality depends on:

- geometry;
- material choice;
- texture scale/repeat;
- roughness/reflectivity;
- lighting;
- surrounding context.

Do not use a structurally-correct white/default material as a finished state.

# 4. Scene environment and camera

## Environment is scene-level presentation state

Sky/HDRI/EXR, background, sun/time, exposure, scene tint, fog, table/background presentation, bloom/filtering and scene lights materially affect whether geometry is readable.

Never transplant environment flags blindly from an unrelated working Scene. A working exterior and a working subterranean dungeon require different presentation.

## Camera placement must be validated against runtime bounds

3D Canvas camera coordinates are 3D-world coordinates, not Foundry pixel coordinates.

Correct workflow:

1. inspect live runtime Tile bounds;
2. derive target/position in 3D world units;
3. set/frame camera;
4. wait until 3D Canvas is ready;
5. capture;
6. visually inspect.

Do not derive the camera from Region pixel coordinates without an explicit coordinate transform.

## Save initial views deliberately

Use saved initial camera positions for:

- scene entry;
- major room reveals;
- canonical QA stations.

Use temporary camera positions for close-up QA. Do not overwrite presentation cameras simply to inspect a prop.

# 5. Lighting

## Foundry AmbientLights work in 3D, but 3D lighting has different costs

Baileywiki's Foundry Basics lighting principles still apply: lights define visible/intended atmosphere; color, radius, animation and activation conditions matter.

3D Canvas-specific constraints:

- normal 3D lights do not automatically cast physically blocked shadows from every wall/tile;
- shadow-casting/wall-blocking can be enabled per light;
- it is expensive;
- current 3D Canvas documentation recommends only roughly 2–3 shadow-casting/wall-blocking lights per Scene.

Use many cheap atmosphere lights only when needed and keep expensive shadow lights scarce and deliberate.

## Create many lights in 2D when practical

3D Canvas recompiles shaders when lights are added, which can stutter/freeze temporarily. The current docs specifically recommend creating many lights in 2D and then positioning them in 3D.

## Lighting QA must distinguish darkness from renderer failure

A fully black/white/blank 3D capture is not automatically “the dungeon is dark.”

Before treating darkness as art direction, verify:

- renderer ready;
- camera intersects/targets known runtime bounds;
- environment loaded;
- visible geometry exists in Three.js runtime;
- a diagnostic light or readable environment can illuminate it;
- no giant probe/wall is occluding the camera.

# 6. Vision / Fog of War

3D Canvas defaults are important:

- Token Vision: on
- Fog Exploration: on
- Use 3D Geometry for sight: off
- 3D Fog of War: off

With the normal default combination, the 3D map is visually revealed and walls handle token visibility. A new map appearing totally black is therefore **not normal default fog behavior**.

Full 3D fog requires explicitly enabling 3D geometry sight calculations and 3D fog. This is more expensive.

For this campaign:

- prioritize visual reliability and playability first;
- use token vision without full expensive 3D fog unless the fiction benefits strongly;
- treat hidden GM state separately from visual fog;
- never expose traps/secrets merely because the geometry is visible.

# 7. Foundry V14 version boundaries

Tutorials span multiple Foundry generations.

## Do not cargo-cult legacy Levels workflows

Foundry V14 introduced core Scene Levels functionality. The old Levels module is retired as a supported long-term architecture, although the current 3D Canvas wiki and installed dependency manifests can disagree during the transition.

Operating rule:

**The installed V14 runtime is authoritative for dependency behavior.**

Do not add/remove Levels, Wall Height or socketLib based only on an older video or a wiki sentence. Inspect the installed module manifests and test on a clone.

## Keep version-specific UI guidance separate from invariant concepts

Invariant concepts worth retaining from older videos:

- Foundry Scene/Actor/Token/Wall/Light/Journal/Table/Playlist model;
- 3D Tiles as the primary 3D building element;
- asset-first placement;
- collision/sight/door semantics;
- camera framing;
- performance-aware lighting;
- modular mapmaking and prefabs;
- environment + materials + lighting as separate presentation layers.

# 8. Baileywiki Foundry Basics findings

The Foundry Basics playlist is primarily valuable for understanding Foundry as a GM-facing application rather than as a JSON database.

## Walls

Wall types encode different behaviors, not just visible lines:

- normal walls;
- terrain/limited walls;
- invisible/non-restrictive variants;
- ethereal/curtain behavior;
- doors/locked/secret doors;
- windows/proximity/attenuation behaviors.

For 3D Canvas, these concepts remain useful for Foundry logic and fallback 2D vision, but actual 3D architecture should usually be Tile-driven.

## Lighting and vision

Separate:

- Scene lighting state;
- token vision;
- fog exploration;
- light source parameters;
- animation;
- wall interactions;
- “provides vision”/special vision behaviors.

Do not debug all visibility problems as one system.

## Rollable Tables

Tables are first-class Foundry data structures. Nested tables, weighted/ranged results, permissions and document references often eliminate unnecessary custom macros.

Campaign implication: encounter flavor, treasure, complications, downtime and franchise events should prefer Tables when appropriate rather than bespoke script logic.

## Playlists and Ambient Sounds

Sound is both Scene context and localized environment.

Important practices:

- use efficient audio formats such as OGG/MP3 rather than huge WAV assets;
- understand playlist playback modes and audio channels;
- use Scene playlists for broad ambience/music;
- use Ambient Sounds for localized diegetic audio;
- walls/occlusion can affect ambient sound behavior;
- Foundry V14 introduces differences from older tutorials, so verify current controls.

Campaign implication: 3D visual scenes should include ambient audio only after geometry/lighting are stable; sound should reinforce location identity, not conceal weak visuals.

## Storage and organization

Do not put project-owned campaign media into module/system directories that may be replaced by updates.

Maintain dedicated project asset storage and stable paths.

Changing file locations breaks references. Therefore released asset paths should be immutable; new versions should normally use new versioned paths rather than silently moving/replacing released files.

Compendiums are cold/storage distribution; world directories are active working state. Do not import every possible compendium entry into the active world.

Blank Scenes/presets can be used to hold reusable placeables, but our semantic asset catalog is the canonical automation-side equivalent.

Release documentation also describes tools such as bridge_health, snapshot_scene and place_or_update_3d_tile, but they are not currently exposed through the connected MCP surface. Never claim or plan around a tool until it is present in the current tool inventory.

## Underlying bridge protocol is broader

The v0.2 bridge protocol supports operations including:

- scene snapshot/clone/create/view;
- scene_update;
- embedded_create/update/delete;
- asset_upload;
- canvas/window capture;
- world list/get/create/update/delete;
- game pause;
- compendium list/search/import;
- 3D runtime inspection;
- 3D camera get/set/frame;
- runtime bounds;
- wait-ready;
- Tile3D inspection;
- 3D Scene inspection;
- asset search;
- true 3D capture.

When a capability is absent from the MCP facade, use the Drive fallback only when it is genuinely necessary and revision-safe.

## Revision checking is mandatory for production writes

Production write sequence:

1. inspect live 3D Scene;
2. record revision;
3. create/retain a recoverable state before risky changes;
4. write with expected revision;
5. re-inspect;
6. validate semantic manifest;
7. capture from canonical camera;
8. visually accept/reject.

A stale revision must fail rather than overwrite newer state.

## Semantic identity

Generated scene objects need stable:

- `flags.acq.semantic_id`
- `flags.acq.build_id`
- provenance
- classification

Semantic IDs are identities, not coordinates. Re-running a build should update the same semantic object rather than duplicate it.

## No implicit pruning

`apply_semantic_objects` is an upsert path. It does not safely imply “anything not in this batch should be deleted.”

Deletion is explicit, high-risk and should use the underlying bridge only after recovery state exists.

## Session Safety Lock

During live play:

- reads/inspection remain allowed;
- writes are blocked;
- camera/capture operations that disturb live presentation are blocked.

Do not defeat this lock.

# 11. QA doctrine

## Visual acceptance gate

An Episode 1 room is not complete until:

1. the expected objects exist structurally;
2. live 3D runtime inspection sees the intended geometry at believable runtime bounds;
3. camera can frame it;
4. the actual 3D renderer produces a nonblank capture;
5. materials and lighting read correctly;
6. the surrounding context supports the fiction;
7. no GM-only helper, hidden token, secret or debug visual leaks to player-facing presentation.

## Build one proven primitive stack before scaling

Before building Areas 3–10:

Create a disposable scratch scene with:

- one properly initialized 3D floor Tile;
- one model-backed wall/prop Tile;
- one ordinary light;
- one installed asset/material;
- a known environment;
- one camera station.

Prove:

- Foundry document state;
- live runtime bounds;
- camera coordinate transform;
- nonblank renderer capture.

Only then scale the exact creation method.

## Small reversible batches

For risky visual infrastructure:

- 1–5 objects first;
- capture;
- accept;
- expand.

Do not send a 100-object visual batch simply because the API supports it.

## Programmatic inspection precedes guessing

When something is not visible, check in this order:

1. active Scene;
2. 3D Canvas active/available;
3. live runtime Tile count;
4. target Tile loaded in Three.js;
5. runtime bounds;
6. camera position/target;
7. occluding geometry;
8. environment/exposure;
9. light state;
10. model/material loading errors.

Do not repeatedly mutate environment/geometry until the failure layer is identified.

# 12. Performance doctrine

Optimize for a playable campaign, not a render demo.

- Prefer modular assets during art direction.
- Merge compatible static Tiles after acceptance.
- Use Repeat for dense repeated vegetation/props where appropriate.
- Minimize sight blockers.
- Limit expensive shadow-casting lights.
- Avoid unnecessary full 3D fog.
- Prefer optimized installed assets over giant bespoke monoliths.
- Test close-up room views and player-perspective views, not only overhead beauty shots.
